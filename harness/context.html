Chapter 02

문맥의 한계

에이전트가 실수를 하면 가장 먼저 떠오르는 처방은 규칙을 더 적어 넣는 것이다. 규칙 문서에 한 줄 추가하고, 배경 설명을 덧붙이고, 관련 파일을 통째로 붙인다. 이 장은 그 처방이 어디서 한계에 부딪히는지를 세 가지 근거로 본다. 입력이 길수록 성능이 떨어진다는 측정, 규칙 문서를 넣어도 성공률은 거의 그대로이고 비용만 늘었다는 실험, 그리고 적어 둔 규칙이 실제로 강제되는 경우가 드물다는 실태조사다.

이 장에서 배우는 것
  • context rot이 무엇이고, 비슷하지만 틀린 정보(방해 문장) 하나가 왜 문제인지 설명할 수 있다.
  • “가장 작은 고신호 토큰 집합, 필요할 때 불러오기” 원칙을 문맥 예산에 적용할 수 있다.
  • 규칙 문서 실험(Gloaguen 외 2026)의 성공률·비용 결과와, 규칙 문서에 남길 내용과 뺄 내용을 구분할 수 있다.
  • 글로 적은 보안 규칙과 실제로 강제되는 통제의 차이를 수치로 말할 수 있다.

01문맥 길이와 성능: context rot

Chroma 연구팀(Hong 외 2025)은 GPT-4.1, Claude 4, Gemini 2.5, Qwen3를 포함한 LLM 18개로 같은 과제를 입력 길이만 바꿔 가며 풀게 했다. 결론은 짧다. 모든 실험에서 입력이 길어질수록 성능이 일관되게 떨어졌다. 이 현상을 context rot이라고 부른다.

“Across all experiments, model performance consistently degrades with increasing input length.”Hong, Troynikov, Huber. Context rot. Chroma Research, 2025

더 눈여겨볼 결과는 방해 문장(distractor)이다. 정답 문장과 주제는 같지만 내용은 틀린 문장을 하나만 섞어도 정답 문장만 있을 때보다 성능이 떨어졌다. 규칙 문서에 비유하면, 예전 규칙과 새 규칙이 함께 적혀 있거나 비슷한 이름의 설정이 여럿 섞인 상태다.

모델에게 일어나는 일을 직접 볼 수는 없지만, 같은 구조의 과제를 사람이 풀어 볼 수는 있다. 아래 실험은 연구실 운영 메모 더미에서 질문의 답을 찾는 과제다. 메모 길이와 방해 문장 개수를 바꿔 가며 몇 번 풀어 보자. 기록은 오른쪽 그래프에 쌓인다.

02원칙: 가장 작은 고신호 토큰 집합

Anthropic(2025)은 컨텍스트 엔지니어링의 원칙을 이렇게 정리한다. 원하는 결과를 낼 가능성을 높이는 가장 작은 고신호(high-signal) 토큰 집합을 찾고, 모든 것을 미리 넣어 두기보다 필요할 때 불러온다. Claude Code의 스킬도 같은 방식이다. 평소에는 스킬의 이름과 짧은 설명만 문맥에 있고, 해당 작업을 할 때 본문을 읽어 들인다.

03규칙 문서의 효과

그렇다면 저장소마다 두는 규칙 파일(AGENTS.md, CLAUDE.md)은 실제로 도움이 될까. Gloaguen 외(2026)는 코딩 에이전트에게 규칙 문서를 넣고 실제 저장소의 이슈를 풀게 했다. 두 조건을 비교했다. SWE-bench 과제에 LLM이 자동 생성한 문서를 넣은 경우, 그리고 개발자가 직접 커밋해 둔 규칙 문서가 있는 저장소의 이슈 모음(논문의 새 벤치마크)이다.

FIGURE규칙 문서를 넣었을 때의 변화 (Gloaguen 외 2026)

요약하면 세 가지다. 성공률은 거의 그대로였고, 어느 조건도 규칙 문서가 없을 때와 통계적으로 차이가 나지 않았다. 비용은 평균 20% 넘게 늘었다. 그리고 내용에 따라 효과가 갈렸다. 모델은 문서의 지시를 잘 따랐지만, 모델 제공사들이 권장해 온 프로젝트 소개 글은 도움이 되지 않았다. 도움이 된 것은 그 프로젝트만의 특이한 작업 방식을 적어 둔 부분이었다.

근거의 범위
이 실험은 SWE-bench 계열의 코딩 과제 기준이다. 논문·덱·보고서 같은 연구 산출물에도 같은 결과가 나온다는 근거는 아직 없다. 저자들도 규칙 문서로 성능을 높이려는 시도는 배포 전에 엄밀하게 평가하라고 결론짓는다.

이 결과를 규칙 문서 작성에 옮기면 기준이 하나 생긴다. 모델이 이미 알거나 스스로 읽어 낼 수 있는 내용은 빼고, 모델이 모르는 그 프로젝트만의 방식만 남긴다. 아래 가상의 연구실 CLAUDE.md 초안으로 연습해 보자.

GAME규칙 문서 다이어트: 남길 줄과 뺄 줄
이 저장소는 역학 코호트 분석 코드를 모아 둔 곳이다 결측 처리에 coalesce()를 쓰지 않는다 R은 통계 분석에 널리 쓰이는 언어다 경로는 here::here()로만 지정하고 setwd()는 쓰지 않는다 코드는 읽기 쉽고 깔끔하게 작성한다 Word·PPT 생성 코드는 마지막에 Office 재저장 단계를 거친다 폴더 구성: data/, R/, output/ 한글이 깨지므로 heredoc·python -c로 파일을 쓰지 않는다
남길 것: 모델이 모르는 고유 방식
뺄 것: 소개·상식·스스로 읽을 수 있는 것
채점하면 남긴 줄만으로 이루어진 규칙 문서의 길이가 표시됩니다.

04적어 둔 규칙과 실제 강제

규칙 문서에 “하지 마라”라고 쓰면, 그것은 모델이 해석하는 자연어 지시다. 반면 Claude Code의 deny 같은 내장 통제는 에이전트가 행동하기 전에 그 행동을 막는다. 두 방식은 같은 보안 목표를 표현할 수 있지만 작동 방식이 다르다. 공개된 CLAUDE.md 파일 481개에서 보안 규칙을 뽑아, 그 규칙과 맞물리는 내장 통제가 있는지 확인한 연구가 있다(arXiv:2608.23550).

나머지 규칙은 모델의 해석에 맡겨져 있다는 뜻이다. 논문은 CLAUDE.md를 쓰기만 하는 채널이라고 부른다. 개발자가 보안 규칙을 적어도, 그 규칙이 강제될지에 대한 피드백을 받지 못한다.

연구실 사례: 금지 규칙과 238번의 차단

같은 일이 연구실 하네스에서도 관찰됐다. 규칙 문서에는 한글이 깨지는 명령 입력 방식(heredoc, python -c)을 쓰지 말라고 적혀 있었다. 그런데 약 4주(2026-09-11~10-05) 동안 에이전트는 이 방식을 계속 시도했고, 훅이 막은 횟수가 기록으로 남았다.
